## Q3 Scoring
Hidden tests can judge: the exact output text of every command (layout in a CLI is text), JSON and CSV structure, exit codes, error lines, unchanged behaviour of the old formats, file bytes. They cannot judge: module structure, duplication, readability, whether the rebuild is easier to change. Two scoring risks are specific to a rebuild. First, `tests/*` is allowed in every task, so an arm can edit visible tests until the suite is green. B7's hidden tests must copy the key visible output checks, and the run record should count changed or deleted visible test files. Second, the spec must be exact enough that the hidden tests do not judge guesses, and loose enough that the task is still a rebuild and not a copy job. `auditor-mini` checks the task text against the hidden tests for this.
- a) (recommended) Machine scoring as primary, plus a blind review of the 3 B7 diff pairs as a secondary that is reported apart and cannot change H1 or H5. Blinding: a `scout` script strips `.sdlc/` and the kit record files, names the pairs X and Y in a seeded order, and keeps the key in a file outside the repository that the customer opens only after scoring. The form is fixed in the pre-registration: for each pair, "which would you merge: X, Y, either, neither" and one line of reason. Limits: n = 1 judge who knows the kit's style, and 3 pairs. It describes, it does not measure. Cost: about 30 to 45 minutes of the customer's time (opinion).
- b) Machine scoring only, as in plan 3.4 a), with design stated as a limit.
- c) Blind review of all 7 tasks: 21 pairs, more of the customer's time, and the same n = 1 limit.
