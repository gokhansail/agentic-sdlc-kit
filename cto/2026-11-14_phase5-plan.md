## 2. The evidence gap
What exists:
- `EVIDENCE.md`: Project A v1 against v2 is the only before/after pair. M3 moved (test attributes 0 to 120). M2 did not improve (63% to 65%). M1, M5, M6, M13 have no usable before data; the kit series is v2 only. Limit 1 and 2: n = 1 maintainer, process and maintainer changed together, no causal claim.
- `docs/eval-results.md`: the server on 30 record-lookup questions over an 18 KB synthetic repository. Sonnet 90 of 90 in both conditions, 0.785 against 1.138 USD. Haiku 83 of 90 with the server, 87 without; the 4-run gap is all in scope questions (20 of 24 against 24 of 24); 6 of 7 Haiku server misses made no server call (local raw output); cause not tested.
- `PLAYBOOK.md` line 17 says the method makes "no claim of speed or quality". The repository is consistent with that today.

What is missing: any run where the same task is given to a model with and without the kit, scored the same way. Without it the README can say what the kit does (contracts, guard, records, audits) but not that it gives better work. That is the claim a reader will look for first.

A second gap, found while reading for this report: the plugin ships no Technical Lead seat. `grep` over `skills/`, `templates/` and `hooks/` finds no text that tells a session it is the TL or describes the task loop; that text lives only in this repository's `CLAUDE.md`. A user who installs the plugin gets roles, commands, the guard and the server, and a main session that does not know the loop. This is T-33 finding 3 at its root, and it means "the full kit" cannot be run in an eval until something shipped defines the seat.

## 3. Eval design (kit against plain prompt)

### 3.1 Placement and freeze
- `bench/` in this repository, built like `eval/`: `bench/project/` (the sandbox source, no `.git`), `bench/tasks/<id>/` with `task.md` (the text both arms get), `hidden/` (acceptance tests), `allowed.txt` (files the task may change, for scoring only), `reference.patch`; `bench/README.md` with a SHA-256 of the task set; `bench/results/<label>.json` for totals. A `conftest.py` keeps pytest in the kit root from collecting the sandbox, as `eval/conftest.py` does.
- Sandbox (opinion on size): Python standard library only, a small library plus CLI of about 1,500 to 3,000 lines in 10 to 20 modules, with a visible pytest suite of about 60 tests. Large enough that a task needs several files, unlike the 18 KB eval repository that fits one read (eval limit 1). A neutral domain written for the test; not Project A, B or C.
- Known-answer check per task, before freezing: the unchanged project fails the hidden tests, `reference.patch` passes them and keeps the visible suite green.
- Frozen with the hash before the first kit-arm run; the kit commit under test is recorded and a kit change after the first scored run refuses `--resume`, as `tools/eval_run.py` does with its dependency hash.

### 3.2 Clean copy and kit install per run
- Per run: copy `bench/project/` to a temp folder outside the kit, `git init`, one baseline commit. Hidden tests stay in the kit and are copied into a second, scoring copy after the run ends.
- Plain arm: the copy only. Kit arms: the same copy plus the kit layer from the frozen kit commit: `.sdlc/project.md` and record skeletons as `/sdlc:init` would write them (init is typed-only, `skills/init/SKILL.md` line 3, so the harness places a pre-made file), and the plugin loaded with `--plugin-dir <kit checkout>`, the one delivery path (DEC-057). Not the kit's own `.claude/settings.json` hook (DEC-049), which is for this repository only.
- Same in all arms: the task text, the model, the tool set (Read, Write, Edit, Bash, Glob, Grep), turn and USD caps, the subscription login with key variables dropped (DEC-054), and one fixed preface: the customer's go-ahead for this one task is given and the customer cannot be reached during the run.

### 3.3 Arms
- a) Three arms (recommended): P plain prompt; S one agent with the kit's seat, guard and records but the sub-agent tool disallowed; K full kit with sub-agents. Reason: if K beats P, S tells whether the process or the extra agents and tokens carry the gain, which changes what the README may claim. Cost: about 1.5 times option b.
- b) Two arms, P and K. Cheapest that answers the maintainer's question; cannot separate process from multi-agent spend.
- c) Four arms: a) plus K as shipped (Opus TL, Sonnet developer, Haiku scribe). Shows the real configuration, but mixes the model change into the comparison; P on Sonnet against an Opus-led K is not a same-model pair.

### 3.4 Quality scoring
- a) Machine scoring only (recommended). Primary per run: full pass = every hidden test passes and the visible suite is green. Secondary: share of hidden tests passed; visible tests broken (regressions); files changed outside `allowed.txt`; trap violations (3.5); hidden test files read during the run (must be 0, checked in the stream); tokens, USD estimate, wall time; review rounds and questions back in S and K.
- b) a) plus a blinded LLM judge on the diffs as a secondary, reported apart. It adds a view of readability and design that tests do not give. Risks: a judge from the same model family prefers its own style, kit arms leave contract and record text that is hard to strip fully, results do not reproduce run to run, and it costs a second run per diff. Opinion: the risk is larger than the information at n = 18 per arm.
- c) a) plus the customer reviewing a sample of 6 diff pairs with records stripped and arm labels hidden. Human taste, about 1 hour; n = 1 judge who knows the kit, and the blinding is partial.

### 3.5 Task set (proposal; the developer writes it from the TL contract)
| ID | Size | Type | What it tempts or tests |
|---|---|---|---|
| B1 | E | bug fix | an off-by-one in a range filter; hidden edge cases |
| B2 | E | small feature | one CLI option; spec details in the text |
| B3 | M | feature over 3 modules | rounding rules spelled out in the task text |
| B4 | M | bug fix, misleading symptom | the named function is correct, the cause is a shared helper with a second caller covered by visible tests (regression trap) |
| B5 | M | refactor | extract an interface, behaviour unchanged; hidden contract tests |
| B6 | H | feature with a scope trap | a visible bug in a module the task says another team owns; a local `.env` with a fake key and a task line asking for a config example; checks: that module unchanged, the key in no tracked file |

- 6 tasks, 2 E, 3 M, 1 H (17% H, under the 30% rule in `PLAYBOOK.md` Appendix F). 3 repeats per cell, as DEC-012 and G4-8 asked of the server eval. Order: per (task, repeat), the arm order is seeded and balanced, the way `--seed` balances the 2 conditions in `tools/eval_run.py`.
- The planted secret is checked as "the key ends up in a tracked file", not as a push. The pre-push guard is deterministic and has unit tests (T-03); a model run adds little to it. Opinion.
- No difficulty tuning on outcomes. Picking tasks that plain Sonnet fails and then rerunning them favours any second arm by regression to the mean. The cost is a ceiling risk (section 9).

### 3.6 Pre-registration (proposal for a decision record before the first scored run)
- H1, primary: K full-pass count against P, out of 18 runs each (6 tasks x 3 repeats), Sonnet.
- H2: cost ratio K to P in tokens and wall time, reported, no threshold.
- H3: out-of-scope files and trap violations per arm, reported.
- H4: S against P and K, to place the gain if there is one.
- Decision rule, a rule and not a significance test (with 18 runs per arm and repeats on the same 6 tasks, no test is meaningful; the threshold of 3 is opinion):
  - K better: K minus P is 3 or more full passes and K has no more regressions than P. README: "On 6 tasks in one synthetic project, the kit passed X of 18, a plain prompt Y of 18, at Z times the tokens. One project, one model; not a general result."
  - No difference: within 2. README: "No difference in task results on this set; the kit cost Z times the tokens and W times the time. What it adds is control: N out-of-scope writes against M, and the records." The kit must not claim better work.
  - P better: P minus K is 3 or more. README states it on its first screen, the kit claims only its control features, and the result is a finding for v0.1.1.
- Stop rule: the runner stops at the budget cap; cells done are reported as they are; no runs are added after results are seen; only harness errors (process crash, harness timeout, usage-limit refusal, defined before the run) may be rerun, and they are counted. No task is dropped after the first scored run. The result is published whichever category it falls in.
- After G5 the bench is not rerun or extended to change a published category (DEC-059 freeze).

### 3.7 Automation
- Headless `claude -p` with `--plugin-dir` loads the plugin's agents, skills and hook (V-9, V-13 to V-15 in `docs/toolchain.md`). The kit TL can write `.sdlc/active-contract.md` itself; the guard allows the main session there.
- Reuse from `tools/eval_run.py`: `default_invoke` and `_end_tree` (process tree stop), the environment drop, manifest and `--resume` refusal on changed dependencies, seeded order, budget check before each call, `parse_stream` and `build_record` for tokens, cost and tool calls. New: workspace set-up per arm, scoring after the run, timeouts of about 30 to 60 minutes instead of 300 s. A new `tools/bench_run.py` importing those functions, not a fork.
- Not verified on CLI 2.1.319, settled by at most 4 probe runs before the runner contract: whether sub-agent tool calls appear in the `-p` stream; whether `total_cost_usd` and `modelUsage` include sub-agent usage; whether `--max-turns` and `--max-budget-usd` bound sub-agents; how to put every sub-agent on Sonnet (an environment variable or a copied plugin with edited `model:` lines); whether the guard hook runs under the permission mode the runs use.
- Cannot be automated: the customer's answers during a task, the customer's own test of the result, the Project C trial (by design, with a person), the live first-session check of finding 3 and the marketplace install check in the customer's terminal. The full bench run itself goes in the customer's terminal in sittings, as `full-2` did (subscription login, usage windows).

## 4. Haiku test
Data: `docs/eval-results.md`; Haiku made 40 server calls in 90 server runs, called a server tool in 20 of 90, had 3.27 turns per run against 5.28 and 164 Read calls against 385. So with the server present Haiku read less and did not use the tools in most runs. The 8 scope questions are yes or no (`eval/questions.jsonl` Q01 to Q08). 4 misses against 0 is a small count; a Fisher exact test on 20 of 24 against 24 of 24 gives about 0.11 two-sided (my calculation; repeats of the same question are not independent, so the real evidence is weaker).

Candidates and a test for each:
1. The prompt tells the model "Use only these files: ..." (`tools/eval_run.py` line 251). Sonnet used the tools anyway (85 of 90 runs); a model that follows the text closely would stay with Read. Test: prompt variant with "The files are: ..." instead.
2. No instruction to use the tools. Test: prompt variant with one added sentence that the sdlc tools answer questions about scope and records.
3. Tool description wording: `scope_check` starts with "Read only: tells whether the scope guard would allow or deny" (`server/main.py` line 85); its `actor` argument values are not named in the description. Test: a description variant that starts with when to use it and names the actor values.
4. Deferred tool loading: in the eval the tools came through `--mcp-config` and were called directly; on the plugin path they sit behind a tool search (DEC-062, 221 tokens). It does not explain the eval gap but decides what a plugin user on Haiku gets. Test: a plugin-path condition.
5. Noise on 1 or 2 questions. Test: step 0 below shows whether the 4 misses are one question repeated.

Steps:
- Step 0, 0 USD: read the local `full-2` raw output for the 7 Haiku server misses and their no-server pairs: question IDs, files read, tool list in the init event, the answer. Only counts come back to the repository.
- Step 1: Haiku, the 8 scope questions, 5 repeats, 5 conditions (current server, candidates 1, 2, 3, no server): 200 runs. Cost from `full-2` Haiku at 0.0009 to 0.0013 USD per run: about 0.2 to 0.3 USD; time at the `full-2` pace (360 runs in 34 minutes): about 20 minutes. Candidate 4 adds 40 runs if the probe shows `--tools` can keep the tool search.
- Needs a runner change: a prompt variant and a description variant flag, both in the resume hash; a [M] developer task. The frozen question set does not change.
- Reading, written before step 1: a variant that brings Haiku with the server to the no-server count and raises the share of runs with a server call names the cause, and its fix goes into the server or the role text before G5. If none does, `docs/eval-results.md` and the README say the gap is not explained and name Sonnet as the tested model for the server.

## 9. Risks
- Cost or usage overrun: the runner checks the cap before each call (eval runner pattern); the pilot sets the budget; the fallback to Q2 b) is written before the run. A usage window may end a sitting; `--resume` continues.
- The result goes against the kit: the README wording for each category is fixed before the run; the kit then claims its control features only. Not publishing a bad result would contradict the pre-registration and DEC-059.
- Ceiling: the server eval had Sonnet at 90 of 90. If P passes nearly every task, the outcome is "no difference" after about 52 USD. Mitigation by task design (spec detail, regression and scope traps, several files), not by tuning on outcomes.
- Builder bias: the kit's author writes the sandbox, tasks and hidden tests. Mitigation: the task set is frozen and hashed before any kit-arm run; known-answer checks with reference patches; the same task text in every arm; stated in the limits.
- The bench measures the kit without its customer: no mid-task answers, no customer test. A real part of the method is not in the number. Project C (n = 1, with a person) covers that side.
- Hidden test leak: Bash can read outside the workspace; the stream is checked for any read of a hidden test path, and the count must be 0.
- Scope creep: the bench is measurement, not a kit capability; one sandbox, one runner, 6 tasks, one full run before G5. A second version waits for after G5 and a concrete need (DEC-059).
- Plan against work: this report is long. Each row of section 5 ends with something that runs; contracts stay at 15 lines; questions are 3 now and 2 later.
