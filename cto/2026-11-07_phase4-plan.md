## 2. Technical foundations
- Python 3.10.4 on this machine, floor 3.10 (DEC-004). SDK `mcp>=2.3,<3`, class `MCPServer` (DEC-013); the range is already in `requirements-dev.txt`, but `pip show mcp` finds no package in this machine's Python (2026-11-07). T-40 step 0: install, record the exact version in `docs/toolchain.md`. Pin: the range in the requirements file, the tested exact version in the toolchain doc.
- Transport: stdio only. No HTTP or SSE code path, no port. Then C-26 does not apply in phase 4.
- Root lock: the root is fixed once at start from what the host provides, never from a tool argument. Every path argument goes through `scope_guard.relative_to_root` (handles `..`, `/` and `\`, case on Windows); a read then also passes `Path.resolve()` containment as in `tools/metrics/inputs.resolve_inside`, which catches a link that the text compare misses. Fewest path arguments possible: tools take record names or IDs, not paths, except `scope_check`.
- No network: an AST test that the `server/` modules import no network module (as the existing stdlib test for the guard, `tests/test_scope_guard.py` line 498), plus one test that runs every tool with socket creation patched to raise. The SDK's own imports are not ours to ban.
- Reuse, not copy: `tools/` stays standard library and never imports `server/` or `mcp` (the guard's stdlib test stays). The server imports `tools.scope_guard` (`load_state`, `check`, `check_contract`, `check_worktree`) and `tools.metrics` record scanners. New shared logic (record map parse, event file totals) goes into `tools/` as a stdlib function with a CLI mode; the server wraps it. Parity tests: the tool answer equals the function answer on the same fixtures. The server defines no glob or path rule of its own.
- Import path: the launcher runs Python with `-I`, which drops the current folder, `PYTHONPATH` and user site-packages. The entry adds the plugin root to `sys.path` itself; a `pip install --user mcp` is not seen under `-I` (relevant for Q2).
- Record map: tools read file names from the `## Records` section of `.sdlc/project.md`; not opted in means template defaults. The map has no lessons line today (`templates/project.md`): T-42 adds one.
- Tests: tool functions in process on `tmp_path` repositories; one stdio round trip through the SDK client (`list_tools`, `call_tool`) as in the T-04 smoke test; live `claude --plugin-dir . -p` runs counted and capped per contract, Haiku, as in phase 3.
- NOT VERIFIED, closed by the first step of T-40 with at most 2 live runs: how the CLI spawns a plugin stdio server on Windows (`sh` launcher or `python` directly); whether `${CLAUDE_PLUGIN_ROOT}` and `${CLAUDE_PROJECT_DIR}` expand in a plugin `.mcp.json`; the server's working folder at start; the tool name the CLI shows for a plugin server.

## 4. Open decisions (block T-40, not T-39 or T-39a)

### Q1 Does the server write records?
Data: `hooks/hooks.json` matches `Write|Edit|NotebookEdit` only, so a server tool call is not seen by the guard. `agents/developer.md` has no `tools:` line and inherits every tool, server tools included; the other 6 roles list their tools. The DEC-012 eval asks questions about state, which read tools answer.
- a) Read-only server in phase 4 (recommended). T-42 tools become lookups; records stay written through the file tools under the guard. Cost: smallest, T-42 [M]. Risk: none to the guard; `DEV_RULES.md` rule 7 ("the server reads and writes them") is narrowed for this phase, which this option contradicts and the TL records. Reversible: write tools can come later with b).
- b) Write tools, and the hook matcher extended to them: the guard maps each tool to its record file and decides as for a Write. Cost: one probe (does PreToolUse fire on a plugin server tool with `agent_id`), matcher, tests; T-42 [H]. Risk: a new path into the guard in its last phase before release.
- c) Write tools, sub-agents kept away only by role `tools:` lists. Cost: low. Risk: a convention, not a check; how plugin agents treat server tool names in `tools:` is not verified.

### Q2 How does a user get the `mcp` SDK?
Data: the plugin has no install step (DEC-040); `uv` 0.13.6 is on this machine but not in the toolchain doc; whether a user has it: could not read.
- a) The user installs the SDK into the Python the launcher finds; the launcher checks the import and version range and fails with a one-line install hint (recommended for phase 4). Cost: none beyond the launcher. Risk: a manual step; `--user` installs are not seen under `-I`. The user-facing path is decided in phase 5 with b) or c) as candidates. Reversible.
- b) `.mcp.json` starts the server through `uv run` with the pinned dependency. Cost: uv becomes a requirement. Risk: a network fetch at first start; offline machines fail.
- c) A typed command creates a virtual environment in the plugin data folder once, with the customer's word. Cost: one more skill. Risk: a new command and its tests in this phase.
