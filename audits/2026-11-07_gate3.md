### C-1 The test suite is red on a fresh Windows clone
- Type: code
- Severity: Medium
- Claim: `python -m pytest -q` green is the push precondition (`CLAUDE.md`) and the G3-2 and G3-9 evidence; the skills and the pattern template are LF-only (`tests/test_skills.py` `test_line_limit_ascii_and_lf`, `tests/test_install_target.py` `test_template_is_ascii_and_lf_only`).
- Evidence: `.gitattributes` pins `eol=lf` for `hooks/**`, `*.py` and `*.sh` only; 69 tracked files (49 `.md`, 14 `.json`, 3 `.txt`, 3 others) have no attribute, all LF in the index. `core.autocrlf` is `true` on this machine. In the build folder the 5 `SKILL.md` files and `templates/guard-patterns.txt` are `i/lf w/lf` (`git ls-files --eol`), so the suite passes here. In a fresh `git clone` of HEAD into a scratch folder the same files are `i/lf w/crlf`, and the 6 tests named above fail; full suite there 6 failed, 499 passed, 1 skipped in 122 s (HEAD alone, 505 tests; the 10 T-33b tests are uncommitted). The G2 report already saw the effect in throwaway clones ("7 of 7 equal once line endings are normalized") and the CTO plan noted that `.gitattributes` has no rule for `.md`; no record says the suite fails on a clone.
- Why it matters: the first thing a stranger, or `auditor-mini` in a throwaway clone, runs is red; the test that was written to protect LF cannot tell a real regression from a checkout setting. The installer copies the template from the plugin folder, so a CRLF checkout of the plugin would also ship `\r` into a target's pattern file; the guard's `splitlines()` tolerates it, so the hook still works.
- Recommendation: add `*.md text eol=lf` and `*.txt text eol=lf` (or `skills/** text eol=lf` and `templates/** text eol=lf`) to `.gitattributes`, run `git add --renormalize .`, and rerun the suite in a fresh clone. One [E] task; the fix belongs in the G3 fix round so that the re-verification clone is green.
