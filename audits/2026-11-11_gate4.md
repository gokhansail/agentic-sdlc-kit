### S-1 The `changed_outside` tool starts a program from a git config in 2 layouts
- Type: security and privacy
- Severity: High
- Claim: `docs/security.md`: S-3 is FIXED ("`changed_outside` now refuses a config with `[filter` or `[include`, and a `.git` that is a file or a link"); "Open High: 0"; its scale says "High: a tool can read or leak data outside the root, reach the network or run code". LOG 2026-11-08 (7): "0 open (G4-9 met)".
- Evidence: own probes in scratch folders outside the repository, kit code of HEAD 3a699e0, git 2.35.1, Windows 10, Python 3.10.4. Each project has the fixture project file and contract and a tracked text file whose time changed. The filter program only appends a line to a marker file. Each probe has a control run without the filter: 0 lines.
  1. Nested repository. The project's index holds a folder as a gitlink (mode 160000, no `.gitmodules` needed), and the nested repository's own config names a clean filter. `git_problem` reads only the config of the repository at or above the root (`server/inputs.py` lines 77 to 97) and returned no problem. `changed_outside` answered `ok` true, "0 changed paths", and the marker had 1 line. This is the "submodule configs" part of S-4, filed as Low, ACCEPTED, "No test".
  2. Root laid out as a git folder. The project root itself holds `HEAD`, `objects/`, `refs/`, `index` and `config`, with `core.worktree = .` and a clean filter in that `config`, and no `.git` entry. `git_problem` looks only for a `.git` entry (line 79), found none and returned no problem. `changed_outside` ran git and the marker had 1 line. This layout is not in `docs/security.md`.
  In both, `_git` passes `-c core.fsmonitor=false` and nothing else (`tools/scope_guard.py` line 573). Checked in scratch, not as a fix: `git status --ignore-submodules=all` gave 0 filter runs in layout 1; an explicit `--git-dir <root>/.git` made git refuse layout 2 with 0 filter runs.

The exposure, stated plainly: it needs a crafted folder that is opted in and holds an active contract, and a model that calls the tool; any other `git status` in such a folder, by a person or a tool, starts the same filter. S-4 gives a reason for the system and global config ("the owner controls the last two") and none for nested repositories. The role that built the server also wrote the pass; the T-44 contract left the re-check to this gate.
- Recommendation: one fix task that closes both layouts in the server path or in `_git`, each with a test that has a control run, as S-2 and S-3 have, and updates the S-3 and S-4 rows. Or the customer accepts the risk in a decision, S-4 is rated again with its reason, and the limits say that the tool can start a program from a nested or root-level git config. The first option changes what `--check-worktree` reports for a changed nested repository; the TL weighs that. `auditor-mini` re-verifies either way. `/sdlc:review` runs the same `git status` from the CLI with no config check; that is the user's own command and was outside T-44, and the limits should say so.
